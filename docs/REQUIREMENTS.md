# 요구사항 명세서

## 목적

- 사용자의 식단 기록, 영양 분석, 학교 식당 메뉴 비교 서비스를 제공하기 위해 필요한 데이터와 처리 범위를 정의한다.
- 회원, 학교 인증, 건강 프로필, 음식 영양성분, 식당 메뉴 데이터를 데이터베이스에 어떻게 저장하고 활용할지 정리한다.

## 데이터베이스 요구사항

1. 회원은 이메일, 비밀번호, 이름, 나이를 입력하여 가입할 수 있어야 한다.
2. 회원가입 시 사용자가 대학교를 직접 선택하지 않고, 이메일 도메인으로 대학교를 자동 판별해야 한다.
3. 이메일 도메인이 등록된 대학교 도메인과 일치하면 해당 대학교 회원으로 저장하고, 일치하지 않으면 일반 사용자로 저장해야 한다.
4. 일반 사용자는 학교 식당 메뉴 비교 기능을 사용할 수 없어야 한다.
5. 학교 회원은 학교 이메일 인증을 통해 본인이 해당 대학교 소속임을 인증할 수 있어야 한다.
6. 학교 이메일 인증코드는 영구 보관 대상 데이터가 아니며, 인증 처리를 위한 임시 해시 또는 임시 저장소로만 관리해야 한다.
7. 회원은 로그인하면 인증 토큰을 발급받고, 로그아웃하면 해당 토큰은 더 이상 사용할 수 없어야 한다.
8. 회원은 탈퇴할 수 있으며, 탈퇴 시 회원과 관련된 인증 정보, 프로필, 식단 기록이 함께 삭제되어야 한다.
9. 회원은 성별, 키, 몸무게, 목표 몸무게를 건강 프로필에 등록할 수 있어야 한다.
10. 회원의 BMI는 입력된 키와 몸무게를 기준으로 자동 계산되어 저장되어야 한다.
11. 대학교는 대학교번호와 대학교명으로 식별되어야 한다.
12. 대학교별 학교 이메일 도메인을 관리하여 학교 이메일 인증과 대학교 자동 판별에 사용할 수 있어야 한다.
13. 인하대학교에는 생활관 식당과 학생 식당 정보를 저장해야 한다.
14. 생활관 식당은 점심과 저녁 메뉴를 관리해야 한다.
15. 학생 식당의 점심 메뉴는 한상한담, ONE PLATE, Noodle, 셀프라면 등의 구분으로 관리해야 한다.
16. 학생 식당의 저녁 메뉴는 석식 구분으로 관리해야 한다.
17. 식당 메뉴는 날짜, 식당, 끼니, 메뉴 구분, 메뉴명 정보를 유지해야 한다.
18. 식당 메뉴 가격 정보는 필수 저장 대상에서 제외한다.
19. 인하대학교 학생 식당 메뉴는 학교 식단 페이지를 크롤링하여 저장해야 한다.
20. 학생 식당 메뉴는 매주 월요일에 한 번씩 크롤링하여 갱신해야 한다.
21. 인하대학교 생활관 식당 메뉴는 매달 제공되는 PDF 식단표에서 점심/저녁 메뉴를 추출하여 저장해야 한다.
22. 생활관 PDF 원본 파일은 DB에 직접 저장하지 않고, 파일에서 추출한 날짜/끼니/메뉴 데이터를 DB에 저장해야 한다.
23. 식당 메뉴 데이터는 매일 바뀌는 데이터이므로 음식 마스터 데이터와 분리하여 관리해야 한다.
24. 음식 마스터 데이터에는 식품의약품안전처 식품영양성분 데이터의 음식명, 식품분류, 기본 제공량 정보를 저장해야 한다.
25. 음식별 영양성분은 열량, 탄수화물, 단백질, 지방, 당류, 나트륨을 기준으로 저장해야 한다.
26. 음식의 영양성분은 100g 기준 값으로 저장하고, 데이터에 제공된 식품중량 또는 기본 제공량을 이용해 1인분 기준 영양성분을 계산할 수 있어야 한다.
27. 사용자는 음식명을 검색할 수 있어야 하며, 검색 결과에서 하나 이상의 음식을 선택할 수 있어야 한다.
28. 사용자는 날짜, 끼니, 메모를 입력하여 식단 기록을 생성할 수 있어야 한다.
29. 사용자는 생성된 식단 기록에 검색한 음식을 여러 개 추가할 수 있어야 한다.
30. 식단 기록 항목에는 음식번호, 음식명 스냅샷, 섭취량, 제외 여부가 저장되어야 한다.
31. 사용자는 잘못 추가한 식단 항목을 삭제하지 않고 제외 처리할 수 있어야 한다.
32. 시스템은 하루 동안 기록된 식단의 총 열량, 탄수화물, 단백질, 지방, 당류, 나트륨을 계산할 수 있어야 한다.
33. 하루 영양 합계는 식단이 변경될 때마다 별도로 저장하기보다 조회 시점에 계산하는 것을 기본으로 한다.
34. 시스템은 한국인 영양소 섭취기준을 바탕으로 사용자의 하루 식단에 대한 경고문구를 제공할 수 있어야 한다.
35. 탄수화물, 단백질, 지방 비율은 각 영양소의 g 값을 kcal로 변환하여 전체 열량 대비 비율로 계산해야 한다.
36. 사용자는 생활관 식당 메뉴와 본인이 선택한 학생 식당 메뉴를 비교할 수 있어야 한다.
37. 식당 메뉴 비교 결과에는 각 메뉴의 열량, 탄수화물, 단백질, 지방, 당류, 나트륨 정보가 포함되어야 한다.

## 운영 관리 요구사항

1. 외부 API 인증키와 메일 발송 계정 정보는 깃허브에 올라가지 않도록 로컬 환경변수 파일로 관리해야 한다.
2. 식품 데이터 파일, PDF 식단 파일 등 원본 데이터 파일은 깃허브에 올라가지 않도록 관리해야 한다.

## 설계 메모

- Swagger 문서화는 프론트엔드 협업에는 필요하지만, 데이터베이스 요구사항 명세서의 핵심 항목은 아니므로 API 명세서에서 별도로 관리한다.
- 음식 데이터 출처는 사용자 요구 데이터에서는 제외하지만, 여러 공공데이터를 병합하거나 중복을 제거할 수 있도록 내부 식별용 출처 컬럼은 유지하는 것이 좋다.
